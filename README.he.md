# AgentGuard: מנוע סיכונים לפני חתימה (אב-טיפוס, שלב 2)

[English](README.md) | **עברית**

> עסקה תקינה מבחינה טכנית אינה בהכרח עסקה מורשית.

AgentGuard מקבל תשלום שסוכן AI רוצה לחתום עליו, ומחליט **APPROVE / REVIEW / BLOCK** (אישור / בדיקה ידנית / חסימה) *לפני* שהחתימה קורית. כל החלטה מגיעה עם קודי סיבה, ראיות ורשומת ביקורת שמשורשרת ב-hash.

- **שלב 1: הזרקת כתובת תשלום (תרחיש A).** המשתמש מאשר "שלם ל-Acme ‏50 USDC". אחר כך הסוכן קורא חשבונית שיש בה הוראה נסתרת שמחליפה את כתובת היעד.
- **שלב 2: מנדטים חתומים והתנהגות לאורך זמן (תרחיש C).** המשתמש חותם ב-Ed25519 על מנדט מובנה: יעדים, תקרה לתשלום, תקציב כולל, מספר תשלומים, חלון תוקף והסוכן המורשה. המנוע מאמת את החתימה ואוכף את המנדט על *רצף* תשלומים בעזרת יומן (ledger) משלו. היומן תופס חריגה מצטברת מהתקציב, פיצול תשלומים ופרצי פעילות.

**סטטוס:** אב-טיפוס מחקרי, בלי כסף אמיתי. מדדי המנוע נמדדו על נתונים סינתטיים. השירות האוכף רץ גם מקצה לקצה על רשת הבדיקה Base Sepolia (ראו "השירות האוכף").

## איך מתקבלת ההחלטה

| עיקרון | מימוש |
|---|---|
| אמון מגיע רק מהמשתמש ומהארגון | יעדים מאושרים מגיעים מ-`UserIntent.approved_destinations` ומ-`AuthorizationPolicy.vendor_registry`. פריטי הקשר (חשבונית, מייל, אתר, API) הם **תמיד** לא אמינים. התווית `source_type` שלהם תיאורית בלבד ולעולם לא מעניקה אמון (מקרה A10). |
| כללים דטרמיניסטיים מחליטים | כל בדיקה מפיקה `Finding` בחומרה `block` / `review` / `info`. ההחלטה היא החומרה הגבוהה ביותר שנמצאה. ציון הסיכון מוצג אבל לא משמש להחלטה. |
| זיהוי הזרקה הוא ראיה, לא הבקרה | הסורק מבוסס regex (`injection.py`) מסביר *למה* כתובת השתנתה. כתובת שהוחלפה עם ניסוח נקי לגמרי עדיין נחסמת (A13). חשבונית עם הזרקה שהסוכן התעלם ממנה עדיין עוברת (A04). |
| כשל סגור (fail closed) | אין כתובת אמינה ברשומות → REVIEW. חריגה במנוע → REVIEW (`ENGINE_ERROR`). |
| יומן ביקורת שחושף שינויים | כל רשומה ב-SQLite מחזיקה `prev_hash` ו-`record_hash`. עריכה של שורה כלשהי שוברת את `verify_chain()`. |

### קודי סיבה

| קוד | חומרה | משמעות |
|---|---|---|
| `DESTINATION_NOT_AUTHORIZED` | block | יש כתובת אמינה לנמען הזה, והיעד אינו אחת מהן |
| `LOOKALIKE_ADDRESS` | block | אותה התחלה וסוף גלויים כמו כתובת מאושרת (הרעלת כתובות) |
| `DENYLISTED_DESTINATION` | block | היעד ברשימה השחורה של הארגון |
| `INVALID_ADDRESS_FORMAT` | block | לא כתובת EVM תקינה |
| `AMOUNT_EXCEEDS_POLICY_LIMIT` | block | מעל התקרה לעסקה |
| `AMOUNT_ABOVE_INTENT` | block | מעל מה שהמשתמש אישר (כולל טווח סטייה) |
| `TOKEN_/CHAIN_NOT_ALLOWED`, `TOKEN_/CHAIN_MISMATCH_INTENT` | block | הנכס או הרשת שונים מהמדיניות או מכוונת המשתמש |
| `AGENT_NOT_AUTHORIZED` | block | המדיניות שייכת לסוכן אחר |
| `UNVERIFIED_DESTINATION` | review | אין כתובת אמינה ברשומות, ולכן אי אפשר לאמת את היעד |
| `TRUSTED_SOURCES_CONFLICT` | review | הכתובת שהמשתמש אישר ורשימת הספקים לא מסכימות |
| `AMOUNT_BELOW_INTENT` | review | תשלום נמוך ממה שהתבקש |
| `PAYEE_MISMATCH` | review | שם הנמען של הסוכן שונה משל המשתמש |
| `PROVENANCE_MISMATCH` / `PROVENANCE_MISSING` | review* | המקור שצוטט לא מכיל את הכתובת, או שלא סופק |
| `DESTINATION_VERIFIED` | info | היעד תואם רשומה אמינה |
| `DESTINATION_FROM_UNTRUSTED_SOURCE` | info | מאיפה הסוכן לקח את הכתובת הלא מאומתת |
| `UNTRUSTED_ADDRESS_IN_CONTEXT` | info | כתובת לא מאושרת הופיעה בהקשר ולא נעשה בה שימוש |
| `INSTRUCTION_IN_UNTRUSTED_CONTENT` | info | נמצא טקסט שנראה כמו הוראה בתוכן חיצוני |

\* יורדים ל-`info` כשהיעד כבר מאומת.

## שלב 2: מנדטים והתנהגות

| עיקרון | מימוש |
|---|---|
| סמכות חייבת להיות חתומה | `SignedMandate` = גוף + חתימת Ed25519 על JSON קנוני. שורש האמון הוא `policy.principal_keys` (הגדרות הארגון). כל עריכה בגוף שוברת את החתימה (M02). מפתח בחתימה עצמית או מזויף נדחה (M03, M04). |
| מנדט הוא ממצה | כשמנדט מגדיר יעדים, רשימת הספקים לא יכולה להרחיב אותם (M10). `intent` לא חתום באותה בקשה מתעלמים ממנו (M09). עם `require_signed_mandate`, בקשה בלי מנדט נחסמת (M08). |
| ההיסטוריה שייכת למנוע, לא לסוכן | `Ledger` (SQLite) רושם רק תשלומים שה-Guard אישר, ואישורים ידניים של REVIEW. סוכן לא יכול להשמיט היסטוריה שמעולם לא שלט בה. |
| אין חריגה בגלל תחרות בין בקשות | `Guard.check()` קורא היסטוריה, מחליט ושומר מקום בתוך נעילת `BEGIN IMMEDIATE` אחת. בדיקה שולחת 8 בקשות במקביל לתקציב של 4 תשלומים: בדיוק 4 עוברות. |
| פיצול ≠ חזרה | פיצול = לפחות 2 תשלומים לאותו יעד, כל אחד לפחות 50% מהתקרה לתשלום, שסכומם עובר את התקרה תוך 24 שעות → REVIEW. מיקרו-תשלומים (C06) וחזרה חודשית (C07) לא נחשבים. אם המנדט החתום מאשר במפורש את הסכום הכולל (C01), הדפוס נרשם כ-info בלבד. |

| קוד | חומרה | משמעות |
|---|---|---|
| `MANDATE_REQUIRED` / `_UNKNOWN_SIGNER` / `_INVALID_SIGNATURE` | block | אין מנדט, המפתח לא רשום לאותו גורם מאשר, או שהתוכן שונה או זויף |
| `MANDATE_EXPIRED` / `_NOT_YET_VALID` / `_AGENT_MISMATCH` | block | מחוץ לחלון התוקף, או ניתן לסוכן אחר |
| `AMOUNT_ABOVE_MANDATE` | block | מעל התקרה לתשלום שבמנדט |
| `CUMULATIVE_BUDGET_EXCEEDED` / `TX_COUNT_EXCEEDED` | block | יעבור את התקציב הכולל או את מספר התשלומים של המנדט |
| `SPLIT_PAYMENT_SUSPECTED` | review | תשלומים קרובים לתקרה לאותו יעד מצטברים מעבר לתקרה |
| `VELOCITY_LIMIT` | review | יותר מ-N תשלומים של הסוכן בחלון הזמן (ברירת מחדל 10 ב-60 דקות) |
| `HISTORY_UNAVAILABLE` | review / info | לא מחובר יומן. REVIEW אם למנדט יש תקרות מצטברות (כשל סגור) |
| `SPLIT_PATTERN_WITHIN_MANDATE`, `BUDGET_OK`, `MANDATE_VERIFIED`, `REQUEST_INTENT_IGNORED` | info | ראיות |

## השירות האוכף (v2)

עד עכשיו המנוע רק *המליץ*: סוכן יכול היה לדלג עליו, או לשלוח בבקשה מדיניות ומפתחות משלו. `agentguard/service.py` הופך את הבדיקה לחובה ברמת הארכיטקטורה:

| הסוכן שולט ב- | השירות שולט ב- |
|---|---|
| התשלום שהוא מבקש, ומה שהוא קרא | **מי הסוכן.** הכותרת `X-Agent-Key` קובעת; נשמר רק hash של SHA-256 של המפתח |
| | **המדיניות שלו ומפתחות הגורמים המאשרים.** `Store` בצד השרת, נטען מהגדרות ה-Excel; בקשה שמכילה `policy`, ‏`agent_id` או שדה לא מוכר נדחית עם 422 |
| | **מפתח החתימה.** רק `Signer` יכול להעביר כסף, והוא נקרא רק ב-APPROVE |
| | **כמה פעמים בקשה משולמת.** `(agent, request_id)` נרשם; ניסיון חוזר מקבל את התשובה השמורה (`replayed: true`), וניסיונות מקבילים מקבלים 409 |

השירות גם רושם את ה-tx hash ששלח, כך ש-Reconcile תמיד מקשר לפי hash. `GET /v2/reconcile` משווה את היומן לשרשרת.

**בדיקת האצלה של EIP-7702** (`agentguard/delegation.py`). מאז עדכון Pectra, ארנק רגיל יכול להאציל את הקוד שלו לחוזה עם הרשאה חתומה אחת. כך ארנקי "sweeper" משתלטים על ארנקים. לפני שה-Guard מחליט, השירות קורא `eth_getCode` לארנק המשלם וליעד:
- האצלה (`0xef0100` + כתובת המואצל) על הארנק של השירות עצמו היא BLOCK ‏(`SOURCE_WALLET_DELEGATED`), כי השירות חותם רק על העברות type-2 ולעולם לא על הרשאת type-4.
- האצלה על היעד היא REVIEW ‏(`DESTINATION_7702_DELEGATED`), כי גם ארנקי smart-account לגיטימיים מאצילים, אלא אם המואצל ברשימה אמינה.
- שרשרת שאי אפשר לקרוא ממנה → REVIEW.

`scripts/testnet_7702_setup.py` יוצר ארנק מואצל אמיתי ב-Base Sepolia ‏([עסקת type-4](https://sepolia.basescan.org/tx/0x8a6c3e9deadb81f5eed131a459e370995eae1279b96c4c7018cd169eff6981e4)), ושלב 4b בדמו מקבל REVIEW על תשלום אליו, בקריאה חיה מהשרשרת. מגבלות: זו קריאה בנקודת זמן, כך שהאצלה שנקבעה אחרי הבדיקה לא נראית; ואין לנו נתונים כדי לקבוע אילו מואצלים אמינים.

זה מראה שמסלול האכיפה עובד מול שרשרת אמיתית. זו לא פריסה לייצור: מפתח ה-testnet הוא קובץ רגיל, ואין HSM/MPC. **לא נבנה:** ניהול מפתחות לחתימת השירות (HSM/MPC), החלפה או ביטול של מפתחות סוכנים, ו-TLS או הגבלת קצב לשירות ה-HTTP. נקודת הקצה v1 ‏(`agentguard/api.py`) עדיין מקבלת מדיניות מהקורא. היא נקודת קצה מחקרית ואסור לחשוף אותה.

## שלב 3: Reconcile (מה אושר מול מה בוצע)

AgentGuard מחליט *לפני* החתימה. Reconcile בודק *אחרי* הביצוע: האם מה שקרה על השרשרת תואם למה שאושר? השרשרת לבדה לא יודעת מה אושר, ולכן חוזה הנתונים כולל שלושה אירועים:

| אירוע | מקור | שדות |
|---|---|---|
| `PaymentApproved` | החלטות APPROVE של AgentGuard + hash הביקורת | request_id, approved_at, ארנק הסוכן, יעד, סכום, טוקן, רשת |
| `PaymentSubmitted` (אופציונלי) | הלוג של המבצע | request_id → tx_hash, ניסיון |
| `PaymentObserved` | השרשרת: לוגים של ERC-20 Transfer וקבלות (`observe_rpc.py`, ‏JSON-RPC לקריאה בלבד) | tx_hash, בלוק, זמן, מ-, אל, סכום, סטטוס |

כל אישור מסתיים בסטטוס אחד בדיוק, וכל יציאת כסף מארנק סוכן משויכת לאישור או מדווחת:

| סטטוס | חומרה | משמעות |
|---|---|---|
| `CONFIRMED` | אין | שולם פעם אחת, סכום ויעד נכונים, מספיק אישורים |
| `PENDING` | נמוכה | בתוך תקופת החסד, או נראה עם פחות מ-12 אישורים |
| `FAILED` | בינונית | נכרה אבל נכשל (revert); בטוח לנסות שוב עם אותו request_id |
| `MISSING` | גבוהה | אושר אבל לא נראה אחרי תקופת החסד, עם או בלי hash מדווח |
| `DUPLICATE` | גבוהה | אישור אחד שולם יותר מפעם אחת (למשל ניסיון חוזר אחרי שהעסקה הראשונה כבר עברה; ראו x402 issue #452) |
| `AMOUNT_MISMATCH` | גבוהה | הסכום שונה; יחס מדויק של חזקת 10 מסומן כבאג סביר של decimals |
| `DESTINATION_MISMATCH` | קריטית | העסקה שבוצעה שילמה למישהו אחר: היא השתנתה אחרי האישור |
| `UNAPPROVED_OUTFLOW` | קריטית | כסף יצא מארנק סוכן בלי אישור: עקפו את ה-Guard |

ההתאמה משתמשת ב-tx hash המדווח כשיש. אחרת היא נופלת לארנק + יעד + סכום מדויק + חלון זמן, וההסבר אומר זאת. **מגבלה ידועה:** בלי hash מדווח, תשלום בסכום שגוי לא ניתן לקשר לאישור שלו. הוא מופיע כ-`MISSING` + ‏`UNAPPROVED_OUTFLOW` (שניהם מסומנים), ולא כ-`AMOUNT_MISMATCH`. יש בדיקה שמתעדת את זה.

## מגבלות ידועות (עובדות, לא הסתייגויות)

1. **האכיפה היא שירות אחד, לא חותם-שותף בלתי תלוי.** שירות v2 מחזיק את מפתח החתימה וחותם רק ב-APPROVE, כך שסוכן שמשתמש בו לא יכול לדלג על הבדיקה. אבל זה מפתח אחד בשירות אחד: בייצור, הבדיקה צריכה לשבת בחותם-שותף של MPC או מדיניות, שחייב לחתום לפני שעסקה תקפה.
2. **גבול האמון זז, הוא לא נעלם.** מנדטים בשלב 2 סוגרים את פער "הכוונה המזויפת", אבל עכשיו מפתח החתימה של הגורם המאשר והגדרות `principal_keys` הם הגבול. ניהול מפתחות (איפה המשתמש חותם, החלפה, ביטול) לא נבנה. אין עדיין רשימת ביטולים: מנדט שדלף תקף עד שהוא פג.
3. **EVM בלבד, ובלי אימות checksum של EIP-55.** זה דורש keccak-256, שאינו בספרייה הסטנדרטית של Python.
4. **הכללים ההתנהגותיים הם ספים קבועים** (50% מהתקרה, 24 שעות, 10 לשעה). הם ממלאי מקום, לא כוילו על נתוני תשלומים אמיתיים, ותוקף סבלני יכול להישאר מתחתם (למשל 3 תשלומים ביום). אי-התאמה סמנטית במטרה (תרחיש B) מתוכננת לשלב 3.
5. **קל לעקוף את ה-regex של ההזרקה.** זה מקובל רק כי הוא אף פעם לא מחליט.
6. **התאמת נמען היא התאמת מחרוזת מדויקת** אחרי נרמול אותיות ורווחים.
7. **שרשרת הביקורת חושפת שינויים, אבל לא מונעת אותם.** מי שיש לו הרשאת כתיבה למסד יכול לכתוב מחדש את כל השרשרת, אלא אם ה-hash האחרון מעוגן במקום חיצוני.
8. **היומן רושם אישורים, לא סליקה.** APPROVE נחשב כשולם, כך שעסקה שנחתמה ונכשלה עדיין נספרת בתקציב (הכיוון השמרני). Reconcile (שלב 3) מזהה את הפער בדיעבד, אבל עדיין לא משחרר את התקציב.
